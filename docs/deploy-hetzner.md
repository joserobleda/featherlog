# Reference deployment: Hetzner + Cloudflare + GitHub Actions

This is how we run Featherlog in production. You don't have to copy it, since [self-hosting.md](self-hosting.md) covers the general case. It is a complete, tested setup if you want something that works end to end:

- an **existing Hetzner Cloud VPS** (Ubuntu or Debian), possibly running other things already
- **Cloudflare** for DNS and as a proxy
- **Cloudflare R2** for uploaded files and for encrypted database backups
- **GitHub Actions** that build the image, deploy `main` to staging and deploy release tags to production

```
GitHub ──push main──▶ build image main-<sha>, edge ──ssh──▶ staging:    /opt/featherlog/deploy.sh
       ──tag vX.Y.Z─▶ build image X.Y.Z, latest   ──ssh──▶ production: /opt/featherlog/deploy.sh (after approval)
```

## 1. Bootstrap the server

Run [`deploy/bootstrap.sh`](../deploy/bootstrap.sh) as root on each server (staging and production):

```sh
ssh root@your-server
curl -fsSL https://raw.githubusercontent.com/joserobleda/featherlog/main/deploy/bootstrap.sh | bash
```

What it does:

- Installs Docker Engine and the Compose plugin if they are missing, and `age` for encrypting backups.
- Creates a `deploy` user in the `docker` group. CI logs in as this user. Change the name with `DEPLOY_USER=…`.
- Creates `/opt/featherlog` with `docker/compose.yml`, `deploy/Caddyfile`, `deploy/deploy.sh`, `deploy/backup.sh` and a `deploy.sh` symlink at the top level.
- Creates `/opt/featherlog/docker/.env` from `deploy/.env.example` with a generated `POSTGRES_PASSWORD` and `AUTH_SECRET`, but **only if the file doesn't exist yet**.
- Installs a daily backup cron job (`/etc/cron.d/featherlog-backup`, 03:23 server time). It does nothing until backups are configured.

It is **idempotent** and plays well with what's already on the box:

- It never enables, resets or rewrites a firewall. If `ufw` is already active, it only adds allow rules for 22/tcp, 80/tcp, 443/tcp and 443/udp. A Hetzner Cloud Firewall, if you use one, is managed in the Hetzner console. Allow 80 and 443 there.
- It doesn't touch an existing reverse proxy. Featherlog's app is published only on `127.0.0.1:3000`, and the bundled Caddy only starts if you ask for it (`USE_CADDY=1`).
- It never overwrites an existing `.env`. Re-running it refreshes the compose file and scripts from `main`.

Then add the CI public key (see [step 5](#5-github-actions)) to `/home/deploy/.ssh/authorized_keys`.

## 2. Configure `/opt/featherlog/docker/.env`

```sh
sudo -u deploy nano /opt/featherlog/docker/.env
```

Production example:

```sh
POSTGRES_PASSWORD=…                         # generated by bootstrap
AUTH_SECRET=…                               # generated by bootstrap
APP_URL=https://changelog.example.com
APP_DOMAIN=changelog.example.com
ACME_EMAIL=ops@example.com
SIGNUP_MODE=invite

SMTP_URL=smtps://user:password@smtp.example.com:465
MAIL_FROM="Example Changelog <changelog@example.com>"

STORAGE_DRIVER=s3
S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
S3_REGION=auto
S3_BUCKET=featherlog-files
S3_ACCESS_KEY_ID=…
S3_SECRET_ACCESS_KEY=…
S3_PUBLIC_URL=https://files.example.com

WORKER_MODE=inline
LOG_LEVEL=info

# Let Featherlog's Caddy own ports 80/443. Leave it out if another proxy already does.
USE_CADDY=1

# Backups (step 4)
BACKUP_S3_BUCKET=featherlog-backups
BACKUP_S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
BACKUP_S3_ACCESS_KEY_ID=…
BACKUP_S3_SECRET_ACCESS_KEY=…
BACKUP_AGE_RECIPIENT=age1…
```

**If the server already runs a reverse proxy** (nginx, Traefik, another Caddy), leave out `USE_CADDY` and point that proxy at `127.0.0.1:3000`. See [behind an existing reverse proxy](self-hosting.md#behind-an-existing-reverse-proxy).

Start it once by hand to check everything:

```sh
sudo -u deploy /opt/featherlog/deploy.sh ghcr.io/joserobleda/featherlog:latest
```

> The server pulls images from GHCR without logging in, so the `featherlog` package must be **public**: GitHub → your profile or org → Packages → featherlog → Package settings → Change visibility. If you keep it private, run `docker login ghcr.io` as the `deploy` user with a read-only token.

## 3. DNS and Cloudflare

1. Create an `A` record (and `AAAA` if the server has IPv6) for `changelog.example.com` pointing at the server, with **Proxied** (orange cloud) on. Do the same for `PUBLIC_URL`/`WIDGET_URL` hosts if you use them.
2. **SSL/TLS → Overview**: set the mode to **Full (strict)**. Caddy holds a valid Let's Encrypt certificate behind Cloudflare. *Flexible* causes redirect loops.
3. Keep **Rocket Loader** and **Email Obfuscation** off for this host. They rewrite HTML and scripts and can break the dashboard and the widget.
4. **Cache the widget assets**. `widget.js` and `/widget/*` already send `Cache-Control: public, max-age=3600, stale-while-revalidate=86400`. Cloudflare caches `.js` and `.css` by default, so these are served from the edge. If you want to be explicit, add a Cache Rule: *URI Path* equals `/widget.js` **or** starts with `/widget/` → *Eligible for cache*, *Respect origin TTL*.

   Don't add cache rules for `/_widget/*` or `/api/widget/*`. Those responses vary by `Accept-Language`, and Cloudflare's standard cache ignores `Vary`, so visitors could get the wrong language. They are cheap to serve and already send `s-maxage=60`.
5. Leave `/api/*`, `/mcp` and `/app/*` uncached. Cloudflare doesn't cache them by default.

## 4. R2 buckets for files and backups

Create two buckets in Cloudflare R2:

| Bucket | Purpose | Settings |
| --- | --- | --- |
| `featherlog-files` | Uploaded images (`STORAGE_DRIVER=s3`) | Connect a custom domain (for example `files.example.com`) and set it as `S3_PUBLIC_URL`. |
| `featherlog-backups` | Encrypted Postgres dumps | Private. Add a lifecycle rule to delete objects under `postgres/` after 30 days. |

Create **R2 API tokens** (R2 → Manage API tokens):

- Server, files: *Object Read & Write* on `featherlog-files` → `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY`.
- Server, backups: *Object Read & Write* on `featherlog-backups` → `BACKUP_S3_ACCESS_KEY_ID` / `BACKUP_S3_SECRET_ACCESS_KEY`.
- GitHub, backup check: *Object Read only* on `featherlog-backups` → `BACKUP_ACCESS_KEY_ID` / `BACKUP_SECRET_ACCESS_KEY` secrets.

The S3 endpoint is `https://<account-id>.r2.cloudflarestorage.com` for both.

Create the backup encryption key **on your laptop**:

```sh
age-keygen -o featherlog-backup.key
```

Put the public key (`age1…`) in `BACKUP_AGE_RECIPIENT` on the server. Store the private key file in your password manager and in the `BACKUP_AGE_KEY` GitHub secret. Never put it on the server. Test with:

```sh
sudo -u deploy /opt/featherlog/deploy/backup.sh
```

Logs from the cron job go to `/var/log/featherlog-backup.log`.

## 5. GitHub Actions

Workflows:

- [`ci.yml`](../.github/workflows/ci.yml): lint, typecheck, unit tests, e2e tests and a Docker build on every PR. It needs no configuration.
- [`release.yml`](../.github/workflows/release.yml): builds and pushes the multi-arch image to `ghcr.io/<owner>/<repo>`, deploys over SSH and publishes `@featherlog/mcp` to npm.
- [`backup-check.yml`](../.github/workflows/backup-check.yml): every Monday at 04:17 UTC, downloads the newest backup, decrypts it, restores it into a throwaway Postgres and counts workspaces.

Create an SSH key pair for deployments:

```sh
ssh-keygen -t ed25519 -N "" -C "github-deploy" -f featherlog-deploy
# featherlog-deploy.pub → /home/deploy/.ssh/authorized_keys on each server
# featherlog-deploy     → DEPLOY_SSH_KEY secret
```

### Secrets and variables

Set these under **Settings → Secrets and variables → Actions**. Use repository level, or environment level for host-specific values.

| Name | Kind | Used by | Value |
| --- | --- | --- | --- |
| `DEPLOY_SSH_KEY` | secret | release | Private SSH key for the `deploy` user. |
| `DEPLOY_USER` | variable | release | SSH user. Optional, defaults to `deploy`. |
| `STAGING_HOST` | variable | release | Staging server hostname or IP. If it isn't set, the staging deploy is skipped. |
| `STAGING_URL` | variable | release | For example `https://staging.changelog.example.com`. Used for the `/healthz` smoke test. |
| `PRODUCTION_HOST` | variable | release | Production server hostname or IP. If it isn't set, the production deploy is skipped. |
| `PRODUCTION_URL` | variable | release | For example `https://changelog.example.com`. |
| `PUBLISH_NPM` | variable | release | `true` to publish `@featherlog/mcp` on version tags. |
| `NPM_TOKEN` | secret | release | npm automation token with publish rights for `@featherlog`. |
| `BACKUP_BUCKET` | variable | backup-check | `featherlog-backups`. If it isn't set, the workflow is skipped. |
| `BACKUP_ENDPOINT` | variable | backup-check | `https://<account-id>.r2.cloudflarestorage.com`. |
| `BACKUP_ACCESS_KEY_ID` | secret | backup-check | Read-only R2 token for the backup bucket. |
| `BACKUP_SECRET_ACCESS_KEY` | secret | backup-check | |
| `BACKUP_AGE_KEY` | secret | backup-check | Contents of `featherlog-backup.key` (the age private key). |

The image is pushed with the built-in `GITHUB_TOKEN`. The workflow already requests `packages: write`.

### Environments with approval

Create two environments under **Settings → Environments**:

- **`staging`**: no protection rules. Every push to `main` deploys.
- **`production`**: turn on **Required reviewers** and add yourself or your team. Optionally restrict *Deployment branches and tags* to tags matching `v*`.

You can put `STAGING_*` and `PRODUCTION_*` values in their environments. The `if:` conditions in `release.yml` read `vars.STAGING_HOST`/`vars.PRODUCTION_HOST` before the job enters its environment, though, so those two must stay **repository variables**.

## 6. Release flow

| Trigger | Image tags | Deployed to |
| --- | --- | --- |
| Push to `main` | `main-<short-sha>`, `edge` | staging (automatically) |
| Tag `vX.Y.Z` | `X.Y.Z`, `X.Y`, `latest` | production (after approval). `@featherlog/mcp` is also published if `PUBLISH_NPM=true`. |

To cut a release:

```sh
# update CHANGELOG.md, bump packages/mcp/package.json if the bridge changed
git tag v0.1.0
git push origin v0.1.0
```

Then approve the `deploy-production` job in the Actions tab. Each deploy job SSHes in and runs `/opt/featherlog/deploy.sh <image> <environment>`, which pulls, restarts and waits for `/healthz`. The job then smoke-tests `<URL>/healthz` from outside.

## 7. Rollback

Deploy the previous image again:

```sh
ssh deploy@your-server
cat /opt/featherlog/deploy/history.log          # every image deployed, newest last
/opt/featherlog/deploy.sh ghcr.io/joserobleda/featherlog:0.1.0 production
```

Or re-run the deploy job of an earlier successful release in GitHub Actions.

Migrations are additive, so the previous version runs on the newer schema. If a release explicitly breaks that, restore the backup taken before the deploy ([restore](self-hosting.md#restore)). Run `deploy/backup.sh` by hand before risky releases.
